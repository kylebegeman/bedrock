Ophelia 0.7 Blueprint

Rewrite Ophelia as one small Go program on each machine. It installs and runs everything the machine needs: builds, certificates, secrets, backups, health checks and alerts. Loom is where you see and approve it all.

This week's recovery and cleanup showed what's missing. The largest gaps are in watching, backing up and retiring things, not in deploying them. Most of the business-launch features were already specified in Ophelia's docs, but never built: moving apps between machines (major features 1 to 4) and builds from git with previews (strategy phase P4).

What 0.7 is

One Go program, a fraction of the size

0.7 is a single ophelia program that works as both the command-line tool and the service running on each machine. It replaces about 80,000 lines of Python, plus the 12,000 lines of glue Loom wraps around Ophelia today (run-cloud-deploy.sh alone is 3,441). There's one app format, one layout on disk and one way to install.

It keeps what worked: app manifests, the host service as the single authority on its machine, recorded releases with real rollback, Caddy at the edge, Docker underneath, and the outbound link to Loom.

Lessons from this week

What happened, and what 0.7 does about it

What happenedWhat 0.7 does
Dragon Writer went down on July 5, and its backups stopped the same day. Nobody noticed for 75 days.Every app gets health checks and a check that its backups are recent. Alerts reach Loom and your phone the same day.
Olive's work survived only because Dragon Writer wrote its own backup script. Ophelia checks the off-site backup settings in an app's manifest but never runs them, so begam.in's settings do nothing.Backups are built in, and they run. Any app with data gets scheduled off-site backups and a weekly restore drill that proves they open.
Nobody knew what ran where: a forgotten Spaceship server, dead Vultr boxes, leftover apps.A fleet inventory in Loom shows every machine, app and domain, with its last deploy, last backup and health.
A fresh server needed Loom's own installer, because host setup was a deferred item on Ophelia's roadmap.ophelia host setup installs and maintains Docker, the firewall, swap, Caddy, a local image registry and OS updates. Running it again is always safe.
Retiring two apps took an hour of hand-archiving, and the deletes still had to be done by hand.ophelia app retire archives an app's data and config to cold storage, verifies the archive, removes the app and cleans up its DNS.
Loom carries workarounds: a 2,000-line rollback script that reaches into Ophelia's internals, a wait for the first certificate, and image-pull steps.Rollback, certificate readiness and image handling are part of every deploy.
A host-wide image prune could delete other apps' images, and image builds share memory with live sites.Every image, volume and network belongs to one app. Each app gets resource limits, and builds run at low priority.
Secrets were written straight into files and ended up inside backups.An encrypted secrets store. Set and rotate secrets from the command line or Loom; they never appear in logs or on command lines.
Both of your servers had updates waiting on a reboot.Maintenance windows: install updates, reboot, and check that every app came back.
A GitHub Actions budget blocked a release, and a machine can't build its own image, because production requires a registry digest.Deploy without Actions: the machine builds from git and keeps images in its own registry, so a push can be a deploy.
Ophelia has three places it keeps state, two web servers that both claim ports 80 and 443, and two APIs, one of them unauthenticated.One layout on disk, one edge, and one authenticated API.
Nothing tests Ophelia on a real server. Its CI has no Docker or VPS lane, and the watchdog bug only showed up in production.Every release is proven on a machine that's wiped and rebuilt from scratch, running every workflow from setup to restore.
New capabilities

What becomes possible

The BrainTreeLabs launchpad

  • ophelia launchTake a product from a repo to live in one step: domain, certificate, database, backups and health checks.
  • Preview deploysEvery branch gets its own throwaway subdomain, removed when the branch merges.
  • Traction signalsRequests, resource use and storage per product over time: the evidence for deciding what graduates.
  • ophelia graduateMove a product and its data to its own machine with a restore drill, a cutover and a way back. These are Ophelia's specified but unbuilt major features 1 to 4.
  • Forge to launchpadProducts built in Loom's Forge deploy straight onto this machine.

Every app

  • Managed PostgresIts own database and role, with backups and restore drills. SQLite apps get continuous off-site copies.
  • Jobs and one-off tasksScheduled jobs, migrations and admin commands, such as Loom's owner code, without improvised containers.
  • DNS that follows the appCloudflare records are created, checked and removed along with the app.
  • Logs and metricsFor each app, with bounded log sizes, streamed to Loom. No renderer sets log rotation today.

Every machine

  • Machines watch each otherEach box checks the other's apps from outside, so a dead machine can't hide its own outage.
  • Capacity warningsCPU, memory and disk headroom, with a warning well before a disk fills.
  • Joins Loom and upgrades itselfEnrollment through Loom's fleet control, and self-upgrades that roll back if the new version fails.
Keep and drop

What carries over

Keep the ideas

  • App manifests, in one new format, with a converter for today's files
  • One service per machine as the authority
  • Recorded releases, receipts and real rollback
  • Caddy at the edge, Docker underneath
  • The outbound, mutually authenticated link to Loom

Drop the baggage

  • Python and its per-release virtual environments
  • The launcher chain behind the 0.6.18 watchdog bug
  • The split between the v1 and v2 layouts and formats, the three state locations and the second web server
  • The unauthenticated local HTTP API (ship api serve)
  • Loom's deploy glue: the deploy script, the rollback script, the data-authority scripts and the Cloudflare origin copy
  • Features nothing uses (to confirm feature by feature)

Decisions for you

Five calls before building

  1. Build it in the same repository under the same name, or start a new one?My pick: the same repo and name, with the Python code archived at 0.6.x.
  2. Where should alerts go: Loom push notifications, email, or a phone service such as Pushover?My pick: Loom first, with email as a fallback.
  3. Should Ophelia manage your Cloudflare DNS records using a zone-scoped API token?My pick: yes, for begam.in and each product domain.
  4. Where should backups go: Backblaze B2 for every app, with a bucket per app or one bucket with a folder per app?My pick: a bucket per app, so an app's keys can't reach another app's backups.
  5. Build 0.7 before moving the personal apps, or move them now on 0.6 and migrate later?My pick: build 0.7 first, and bring Dragon Writer back on today's OVH box in the meantime.
