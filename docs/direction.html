Direction · September 21, 2026

Bedrock Direction

Bedrock hosts any software, puts it on as many kinds of machine as possible, and keeps it running. There are no more milestone releases. It stays on 0.7.x and ships one feature at a time.

This replaces the release ladder in the 0.7 plan, which is delivered and closed. The backlog is still Ideas.

The change

No 0.8, no 0.9, no date for 1.0

The plan had four rungs: 0.7 runs the personal machine, 0.8 wires Loom, 0.9 opens the launchpad, 1.0 keeps the promise. 0.7 is done. The rest is cancelled as a sequence.

Bedrock stays on 0.7.x. Each finished feature is a patch release, cut when it is finished rather than when a group of things is finished. 0.7.2 was the build cache bounded and garbage collection scheduled, and that was the whole release. That is the size a release is allowed to be.

1.0 is still a real bar: a stable manifest, a stable API, upgrade guarantees, a security review and written docs. It is no longer a release that work aims at, and nothing is being sequenced to reach it.

Why

The milestones were solving a problem that does not exist here

A version ladder is how you tell other people what to expect and when. Nobody is waiting on this. It is private infrastructure with one user, and the only real deadline it ever had, moving off the Python estate before something else broke, has passed.

What the ladder cost was real. Work got picked by which rung it sat on rather than whether it was worth doing, which is how the fleet view came to be the next large thing on the list without anyone having asked what it was for. Grouping features also meant nothing shipped until the slowest one in the group did.

Against that, a patch per feature means a change is on both machines the day it is written, and a mistake in it is one feature wide. The build cache fix found two further bugs within an hour of being on a real machine, because it was on a real machine.

Purpose

What Bedrock is for

Take any piece of software, put it on a machine, and keep it alive without thinking about the machine.

Not a Loom deployer. Loom is the largest thing it hosts and the reason it was built, but it is one app in a manifest like any other, and nothing in Bedrock knows its name. The personal sites, braintreelabs.io and anything else are the same shape.

Three things follow from that sentence, and they are the whole roadmap. Any software means the manifest can describe the thing without special cases. Any machine means the machine can be bought, borrowed, racked at home or already running something else. Keep it alive means backups that restore, certificates that renew and a machine that cleans up after itself, without being asked.

Gap one

Any software: the manifest is fine, starting is not

The manifest already describes more than anything currently deployed uses. The obstacle to hosting a new thing is not that Bedrock cannot express it, it is that expressing it means opening an existing app's bedrock.yaml and copying from it, and there is nothing in the repo to copy from.

The work, in the order it is worth doing:

  • Worked examples in the repo. A static site, a single web service, a web service with Postgres and migrations, and a scheduled job. Four files, each one deployable as written. This is the cheapest item here and it removes the most friction.
  • A manifest schema. Editors can then complete and validate a bedrock.yaml while it is being written rather than at deploy time. Already item 15.
  • Redis or Valkey as a declared data service, the way Postgres is. It is the one dependency common enough that hand-rolling it will keep coming up.
  • An adopt path for software that has no Dockerfile. Today the answer is to write one. Whether Bedrock should ever generate one is an open question, not a plan.
Gap two

Any machine: narrower than it sounds

A machine must be Ubuntu 22.04 or 24.04, or Debian 12 or 13, on x86_64 or aarch64, and host setup refuses anything else by name. In practice that covers nearly every VPS worth buying, and a Raspberry Pi running Pi OS, which is Debian.

The harder limit is not the distribution. It is that an app's hostname must resolve to one of the machine's own public addresses. The edge checks this before it will route, and certificates are issued by reaching the machine on ports 80 and 443. A machine in a home rack has neither. It has a private address that public DNS cannot point at, and no inbound path from the internet.

That matters because the stated fleet is VPSes and machines in a home rack. Half of that fleet cannot host a routed app today. Three ways out, in increasing order of what they buy and cost:

  • DNS-01 issuance. Certificates from a Cloudflare API token instead of an inbound connection. Removes the port requirement for certificates, not the reachability requirement for traffic. Small, and useful on its own for internal names.
  • An outbound tunnel from the home machine to something with a public address, so traffic arrives without an inbound port. This is the actual answer for a home rack, and it is the largest single item on this page.
  • Unrouted machines as a first-class kind, for a machine that runs workers, cron jobs and builds and never serves traffic. Cheapest of the three, because it needs the edge to be optional rather than needing new machinery.

Distribution support beyond Debian and Ubuntu is deliberately not on this list. Nothing in the fleet needs it and adding a package manager means maintaining a second setup path forever.

Not doing

The fleet view, and why it is tabled

Item 32 was the next large thing on the old ladder: every machine enrolled with Loom over a mutually authenticated outbound link, with Loom showing every machine, app, deploy, backup, drill, alert and log, and approvals happening there.

It is tabled for as long as the estate is two machines. A fleet view is a way to see more machines than you can hold in your head, and two is not that number. bedrock status over SSH answers every question it would answer. The other side of the trade is an enrollment protocol, signed and scoped commands, replay protection, a cursored event stream and a new mode in Loom, all of which then have to keep working forever.

Revisit it when there are enough machines that forgetting one is plausible, or when someone without an SSH key needs to see the estate. Everything that depended on it is tabled with it: the Core's own lifecycle from inside the app, push alerts, and approval records for agent-run operations.

Working agreement

How work gets picked now

  • One feature, one patch release. It goes to both machines when it is done, not when a group is done.
  • A feature is picked because something is currently annoying or currently broken, not because of where it sits in a list. Ideas is a menu, not a queue.
  • A feature counts as done when it has run on a real machine. Two of the four bugs in the 0.7.2 work were invisible until then.
  • Nothing is built for a fleet, a team or a user who does not exist.
