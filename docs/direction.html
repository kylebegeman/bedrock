Bedrock Direction

Bedrock hosts any software on a VPS, and makes the next VPS cost almost nothing. There are no more milestone releases. It stays on 0.7.x and ships one feature at a time.

This replaces the release ladder in the 0.7 plan, which is delivered and closed. The backlog is still Ideas.

The change

No 0.8, no 0.9, no date for 1.0

The plan had four rungs: 0.7 runs the personal machine, 0.8 wires Loom, 0.9 opens the launchpad, 1.0 keeps the promise. 0.7 is done. The rest is cancelled as a sequence.

Bedrock stays on 0.7.x. Each finished feature is a patch release, cut when it is finished rather than when a group of things is finished. 0.7.2 was the build cache bounded and garbage collection scheduled, and that was the whole release. That is the size a release is allowed to be.

1.0 is still a real bar: a stable manifest, a stable API, upgrade guarantees, a security review and written docs. It is no longer a release that work aims at, and nothing is being sequenced to reach it.

Why

The milestones were solving a problem that does not exist here

A version ladder is how you tell other people what to expect and when. Nobody is waiting on this. It is private infrastructure with one user, and the only real deadline it ever had, moving off the Python estate before something else broke, has passed.

What the ladder cost was real. Work got picked by which rung it sat on rather than whether it was worth doing, which is how the fleet view came to be the next large thing on the list without anyone having asked what it was for. Grouping features also meant nothing shipped until the slowest one in the group did.

Against that, a patch per feature means a change is on both machines the day it is written, and a mistake in it is one feature wide. The build cache fix found two further bugs within an hour of being on a real machine, because it was on a real machine.

Purpose

What Bedrock is for

Take any piece of software, put it on a VPS, and keep it alive without thinking about the VPS.

Not a Loom deployer. Loom is the largest thing it hosts and the reason it was built, but it is one app in a manifest like any other, and nothing in Bedrock knows its name. The personal sites, braintreelabs.io and anything else are the same shape.

The shape of the work is several businesses and several SaaS products, each one getting its own VPS so that its workload, its storage and its blast radius belong to it alone. That means buying a machine is a routine act, not an event, and the thing being deployed onto it is almost always a web app, an API or something else server-side.

Two things follow, and they are the whole roadmap. Any software means the manifest describes the thing without special cases, and starting a new one is quick. Any VPS means machine number nine costs the same as machine number two: buy it, point Bedrock at it, deploy. Keep it alive is the floor under both, and it is the part that already works: backups that restore, certificates that renew, and a machine that cleans up after itself without being asked.

Gap one

Any software: mostly solved

The manifest already describes more than anything currently deployed uses. The obstacle was never that Bedrock could not express a new app, it was that expressing one meant opening an existing app's bedrock.yaml and copying from it, with nothing in the repo to copy from.

bedrock init closed that in 0.7.3. It writes a commented manifest for a web, static, worker or cron app, adds a database on request, and validates what it wrote before it reaches disk, so a generated manifest always loads.

bedrock init api --host api.example.com --postgres

What is left:

  • A manifest schema. Editors could then complete and validate a bedrock.yaml while it is being written rather than at deploy time. This is item 5, dropped before 0.7 and worth reviving now that init exists to pair with it.
  • Redis or Valkey as a declared data service, the way Postgres is. It is the one dependency common enough that hand-rolling it as a worker with a volume will keep coming up.
  • An adopt path for software with no Dockerfile. Today the answer is to write one. Whether Bedrock should ever generate one is an open question, not a plan.
Gap two

Any VPS: make the next one cost nothing

Every VPS worth buying runs Ubuntu or Debian, and bedrock host setup takes one from bare to ready in a single command. The distribution is not the problem. The problem is everything around it.

Standing up a new machine today is five steps, and three of them are typed in by hand:

scripts/install-release.sh 0.7.3 new-box   # get the binary there
bedrock host setup                         # one command, fine
bedrock integration set cloudflare         # typed in, again
bedrock integration set storage            # typed in, again
bedrock integration set email              # typed in, again

The integrations are the cost. Each one is sealed on the machine it was entered on, so the same Cloudflare token, the same B2 credentials and the same SMTP details are retyped on every new VPS. That is fine twice and tiresome at nine, and retyping a credential is how a wrong one gets in.

The work, in the order it is worth doing:

  • Integrations that carry over. integration set already accepts piped field=value lines, so the machinery is there; what is missing is a way to hand a new machine the set the other machines already use, without the values passing through a terminal or a shell history.
  • One command to bring up a machine. Install, host setup and integrations in a single step against a fresh VPS, so buying one and using one are the same act.
  • Bootstrapping a brand new machine. Self-upgrade landed in 0.7.4, so a machine already running bedrock fetches and checksums its own builds. Getting the first binary onto a VPS that has nothing is still a push from somewhere else.
  • A test bed again. The lane is how any of this gets proven on a real machine, and it currently has none: its target became production. A second cheap VPS restores it.

Two things are deliberately not on this list. Distributions beyond Debian and Ubuntu, because nothing needs them and a second package manager is a second setup path forever. And running on a machine in a home rack: it needs an inbound path from the internet that a racked machine does not have, and it is a fun experiment rather than something a business depends on. If that changes, it changes because the rack got a public address, and this page gets revisited then.

Not doing

The fleet view, and why it is tabled

Item 32 was the next large thing on the old ladder: every machine enrolled with Loom over a mutually authenticated outbound link, with Loom showing every machine, app, deploy, backup, drill, alert and log, and approvals happening there.

It is tabled for as long as the estate is two machines. A fleet view is a way to see more machines than you can hold in your head, and two is not that number. bedrock status over SSH answers every question it would answer. The other side of the trade is an enrollment protocol, signed and scoped commands, replay protection, a cursored event stream and a new mode in Loom, all of which then have to keep working forever.

Revisit it when there are enough machines that forgetting one is plausible, or when someone without an SSH key needs to see the estate. Everything that depended on it is tabled with it: the Core's own lifecycle from inside the app, push alerts, and approval records for agent-run operations.

Working agreement

How work gets picked now

  • One feature, one patch release. It reaches every machine when it is done, not when a group is done.
  • A feature is picked because something is currently annoying or currently broken, not because of where it sits in a list. Ideas is a menu, not a queue.
  • A feature counts as done when it has run on a real machine. Two of the four bugs in the 0.7.2 work were invisible until then.
  • Nothing is built for a fleet, a team or a user who does not exist.
